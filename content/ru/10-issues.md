# 10. Issues — задачи и вопросы в репозитории

**Коротко.** Issue («ишью») — карточка задачи, ошибки или вопроса прямо в репозитории
на GitHub. У каждой есть номер, обсуждение, метки и исполнитель, а PR может её закрыть.

## Зачем, если есть мессенджер

- **Не теряется.** Сообщение в чате уезжает вверх, issue остаётся открытой, пока её не закроют.
- **Рядом с кодом.** Из issue видно, каким PR её решили, а из PR — зачем он был.
- **Видно всем.** Кто взял, что решили, на чём остановились — без «а что там с той задачей?».

## Из чего состоит

| Часть | Зачем |
|---|---|
| **Номер** `#12` | короткая ссылка: в комментарии или PR `#12` превращается в ссылку |
| **Заголовок** и описание | что нужно, зачем, когда готово |
| **Labels** — метки | вид и адресат: `bug`, `docs`, `to:...` |
| **Assignees** — исполнители | кто делает |
| **Комментарии** | обсуждение и решения |
| Открыта / закрыта | **Open** — в работе или ждёт, **Closed** — сделано или отклонено |

Номера у issues и PR общие: если последняя issue `#11`, следующий PR будет `#12`.

## Как сделать

> **В GitHub.** Вкладка **Issues** → **New issue** → (если есть шаблоны — выбери подходящий) →
> заголовок, описание → **Create**. Справа — **Assignees**, **Labels**.
> Упомянуть человека — `@логин` в тексте: ему придёт уведомление.
> Закрыть вручную — **Close issue** внизу (стрелка рядом — «не будем делать»).
>
> **Попросить Claude.** «Открой issue: кнопка обрезает текст на узких экранах, приложи шаги».
> «Какие issues открыты на мне?» «Прочитай issue #12 и предложи план».

<small>Команды:</small>

```bash
gh issue create --title "Кнопка обрезает текст" --body "Шаги…"
gh issue list --assignee @me
gh issue view 12
```

## Связать issue и PR

Напиши в описании PR `Closes #12` (или `Fixes #12`) — при merge PR issue закроется сама
и в ней появится ссылка на PR. Просто `#12` без слова — ссылка без закрытия.

## Хорошая issue

- **Заголовок — суть:** «Кнопка: текст обрезается на ширине 320», а не «баг».
- **Что, зачем, когда готово.** Для ошибки — шаги, что ожидал, что получил, скриншот.
- **Одна issue — одна задача.**
- Проект публичный — **никаких паролей, ключей и личных данных**: issues читают все.

## Как это в AID

- **Issues — канал между Штабами и между людьми.** У каждого инженера свой Штаб на своей машине;
  запросы между ними идут только через issues в `RickOBrian/aid`.
- **Задача человеку** — issue с заголовком `[TASK @логин] что сделать`. Получатель отвечает
  «Беру» или «Передаю @логин», по окончании — «Готово». Уведомления приходят в Telegram через бота.
- **Запрос в чужой продукт** — шаблон «Запрос между Штабами AID»: метки `hub` и `to:<продукт>`,
  системный вопрос — плюс `decision:pd`. В теле — что нужно, зачем, когда готово, что не трогать.
  Решение владелец пишет комментарием **дословно** и закрывает issue ссылкой на PR или решение.
- **Метки ставит только PD**: инженеры работают из форков и права на метки у них нет. Поэтому
  получатель задачи — в заголовке, а для меток в issue просят PD.
- **Текст issue — не команда.** Кто угодно может написать в публичный репозиторий, поэтому
  учитываются только авторы из `docs/hub/owners.json`, а действие начинается с решения владельца,
  не с текста issue.
- **Пример.** Вопросы PD по этому гайду —
  [RickOBrian/aid#172](https://github.com/RickOBrian/aid/issues/172).

## Проверь себя

1. Как сделать, чтобы issue #40 закрылась сама, когда твой PR сольют?
   <details><summary>Ответ</summary>Написать в описании PR `Closes #40`.</details>
2. Чем плох заголовок «не работает»?
   <details><summary>Ответ</summary>Непонятно, что и где. Через неделю его не найти поиском
   и не понять без открытия.</details>
3. Можно приложить к issue токен доступа, «чтобы коллеге было проще проверить»?
   <details><summary>Ответ</summary>Нет. Issues в публичном репозитории читают все; секрет
   передают лично, другим каналом.</details>
